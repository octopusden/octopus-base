# Octopus Quality Plugin CI Reference

Operational reference for the `org.octopusden.octopus-quality` convention plugin
(`gradle-quality-plugin/`): the tool versions it pins per release, the Kotlin/JDK
generation each analyzer targets, and the exact report output paths a CI system can
collect. This is the companion to `docs/Octopus JVM Style Guidelines.md` (conventions
and consumer wiring) and `docs/Octopus GitHub Actions Guide.md` (GitHub-hosted CI).

Every version and path below is anchored to a specific plugin source file. Do not
assume "XML and HTML" for a tool unless it is listed here — several analyzers emit only
one machine-readable format.

## (a) Tool-version matrix

### Static-analysis and coverage tool versions

Versions are pinned in `gradle-quality-plugin/gradle.properties`. Three of them
(`checkstyle`, `pmd`, `spotbugs` engine) are injected into the plugin runtime as
`BuildConstants` (generated by the `generateBuildConstants` task in
`gradle-quality-plugin/build.gradle.kts`) and applied by
`gradle-quality-plugin/src/main/kotlin/org/octopusden/octopus/quality/internal/SubprojectConfigurer.kt`.
The Kotlin-coupled tools (detekt, ktlint, kover) are consumer-owned at apply time (declared
in the consumer's `pluginManagement`, see `docs/Octopus JVM Style Guidelines.md`); the values
below are what the plugin build itself pins and tests against.

| Tool | Pinned version | Property (`gradle.properties`) | How / where applied |
|------|----------------|--------------------------------|---------------------|
| detekt | `1.23.8` | `detektVersion` | Consumer-declared via `settings.gradle.kts` `pluginManagement`; plugin build pins it. Configured in `SubprojectConfigurer.configureDetektEarly` |
| ktlint-gradle plugin | `14.0.1` | `ktlintGradleVersion` | Consumer-declared; configured in `SubprojectConfigurer.configureKtlint`. This is the ktlint-gradle *Gradle plugin* version, not a standalone ktlint engine pin |
| kover | `0.9.4` | `koverVersion` | Consumer-declared (Kotlin-only repos); configured in `SubprojectConfigurer.configureKover`. The plugin's own `kover {}` block notes the "Kover 0.9.4 DSL" |
| checkstyle | `10.17.0` | `checkstyleVersion` | `BuildConstants.CHECKSTYLE_VERSION` → `SubprojectConfigurer.configureCheckstyle` (`ext.toolVersion`) |
| pmd | `6.55.0` | `pmdVersion` | `BuildConstants.PMD_VERSION` → `SubprojectConfigurer.configurePmd` (`ext.toolVersion`) |
| spotbugs-gradle-plugin | `6.0.26` | `spotbugsGradleVersion` | Bundled as `implementation` in `build.gradle.kts` (no Kotlin coupling) |
| spotbugs analysis engine | `4.9.8` | `spotbugsVersion` | `BuildConstants.SPOTBUGS_VERSION` → `SubprojectConfigurer.configureSpotBugs` (`ext.toolVersion.set(...)`). Pinned above the plugin default `4.8.x` because only `4.9.x` ships ASM 9.9 / BCEL 6.11, which can read Java 25 bytecode (class file v69); the `4.8.x` default aborts on v69 |
| codenarc | **not pinned** | — | `SubprojectConfigurer.configureCodeNarc` applies the `codenarc` plugin but never sets `toolVersion`, so CodeNarc uses the Gradle CodeNarc plugin's built-in default for the running Gradle version |
| jacoco | **not pinned** | — | Gradle built-in plugin (`SubprojectConfigurer.configureJaCoCo` / `TaskRegistrar.registerJacocoOverallTasks`); uses the JaCoCo tool version bundled with the running Gradle |

### Kotlin / JDK generation targeted

| Aspect | Value | Source |
|--------|-------|--------|
| Plugin build language | Kotlin `2.2.0` | `build.gradle.kts` `plugins { id("org.jetbrains.kotlin.jvm") version "2.2.0" }` |
| Plugin JVM toolchain | JDK `11` | `build.gradle.kts` `kotlin { jvmToolchain(11) }` — minimum CI runtime across target repos |
| Kotlin Gradle plugin compiled against | `1.9.25` | `build.gradle.kts` `compileOnly(...kotlin-gradle-plugin:${kotlinGradlePluginVersion})`; `kotlinGradlePluginVersion=1.9.25` in `gradle.properties` |
| Kotlin generation detekt targets | Kotlin 1.9 / 2.0-era | detekt `1.23.8` (see caveat below) |

### JDK caveat: detekt must run on JDK 21, not JDK 25

detekt `1.23.8` (`detektVersion` in `gradle.properties`) embeds a Kotlin 1.9 / 2.0-era
analysis engine — consistent with the plugin compiling against Kotlin Gradle plugin
`1.9.25`. That analysis engine does **not** support JDK 25 and crashes when the detekt
task runs on a JDK 25 runtime.

Practical rule for CI: **run the detekt (Kotlin static-analysis) job on JDK 21.** This is
distinct from the SpotBugs situation, where the fix was a newer *engine pin* (`4.9.8`) that
adds JDK 25 bytecode support — see the engine-pin comment in
`SubprojectConfigurer.configureSpotBugs`. detekt has no equivalent JDK-25-capable pin at
`1.23.x`, so the mitigation is the runtime JDK, not a version bump. The rest of the build
(compile, tests, coverage, Java analyzers) can run on the repo's normal JDK.

## (b) Consuming from non-GitHub CI

Any CI system (Jenkins, GitLab CI, TeamCity, Bitbucket Pipelines, Buildkite, plain cron)
can drive the same gates GitHub Actions uses. There is no GitHub-specific logic in the
gate tasks — they are ordinary Gradle tasks registered by
`gradle-quality-plugin/src/main/kotlin/org/octopusden/octopus/quality/internal/TaskRegistrar.kt`.

### Aggregate entrypoints

Two root-level aggregate tasks (both in group `verification`) are the entrypoints; a third
combines them.

| Task | Runs | Registered in |
|------|------|---------------|
| `qualityStatic` | All static-analysis tasks across modules: `checkstyleMain/Test/IntegrationTest`, `pmdMain/Test/IntegrationTest` (Java-source modules), `spotbugsMain/Test` (Java-and-no-Kotlin modules), `detekt` + `ktlintCheck` (Kotlin modules), `codenarcMain/Test` (Groovy modules) | `TaskRegistrar.registerQualityStatic` |
| `qualityCoverage` | `test` for all modules, then per-module coverage verification + report: JaCoCo (`jacocoTestReport`, `jacocoTestCoverageVerification`) or Kover (`koverXmlReport`, `koverVerify`), plus the aggregated report/verification (`jacocoOverallCoverageReport`/`...Verification` for multi-module JaCoCo, or `koverMerged*`) | `TaskRegistrar.registerQualityCoverage` |
| `qualityCheck` | `qualityStatic` + `qualityCoverage` | `TaskRegistrar.registerQualityCheck` |

Typical non-GitHub invocation:

```bash
./gradlew qualityStatic --no-daemon --stacktrace
./gradlew qualityCoverage --no-daemon --stacktrace
```

Run the `qualityStatic` job on JDK 21 for Kotlin repos (detekt JDK-25 caveat above).

### Per-analyzer report output paths

Paths are relative to each analyzed module's build directory (`build/`) unless noted as
root/aggregated. **Each row lists only the formats the plugin actually enables** — verified
against `SubprojectConfigurer.kt`. Where a common format is absent it is called out
explicitly so you do not configure collectors for files that will never exist.

| Analyzer | Machine-readable | Human-readable | Not generated | Source (`SubprojectConfigurer.kt`) |
|----------|------------------|----------------|---------------|-------------------------------------|
| detekt | `build/reports/detekt/detekt.xml` (Checkstyle-format XML) and `build/reports/detekt/detekt.sarif` (SARIF) | `build/reports/detekt/detekt.html` | plain text (`txt` explicitly `required.set(false)`) | `configureDetektEarly`: `xml`, `html`, `sarif` = true, `txt` = false |
| ktlint | `build/reports/ktlint/<task>/…` Checkstyle-format XML (one per ktlint task, e.g. `ktlintMainSourceSetCheck`) | plain-text report in the same `build/reports/ktlint/<task>/` dir (the `PLAIN` reporter) | **no HTML, no SARIF** | `configureKtlint`: only `ReporterType.PLAIN` and `ReporterType.CHECKSTYLE` are registered |
| checkstyle | `build/reports/checkstyle/*.xml` | `build/reports/checkstyle/*.html` | — | `configureCheckstyle`: `xml` + `html` = true |
| pmd | `build/reports/pmd/*.xml` | `build/reports/pmd/*.html` | — | `configurePmd`: `xml` + `html` = true |
| spotbugs | `build/reports/spotbugs/*.xml` | `build/reports/spotbugs/*.html` | — | `configureSpotBugs`: `xml` + `html` = true (via `reports.maybeCreate`) |
| codenarc | `build/reports/codenarc/*.xml` | `build/reports/codenarc/*.html` | — | `configureCodeNarc`: `xml` + `html` = true |
| kover (per module) | `build/reports/kover/report.xml` (via `koverXmlReport`) | **not wired** — `koverHtmlReport` exists in Kover but the convention plugin does not depend on it, so `qualityCoverage` does not produce Kover HTML | Kover HTML (unless invoked directly) | `qualityCoverage` wires `koverXmlReport` + `koverVerify` only (`TaskRegistrar.registerQualityCoverage`); `configureKover` sets the verify threshold |
| jacoco (per module) | `build/reports/jacoco/test/jacocoTestReport.xml` | `build/reports/jacoco/test/html/` | — | `configureJaCoCo`: `xml` + `html` = true |

Filenames for checkstyle/pmd/spotbugs/codenarc follow the Gradle convention of one file
per source set (`main`, `test`, …); the directories above are stable, the exact per-set
filenames depend on which source sets a module has.

### Aggregated JaCoCo report (multi-module)

For multi-module JaCoCo repos, `qualityCoverage` also produces a single aggregated report
at the **root** project (registered in `TaskRegistrar.registerJacocoOverallTasks`, with
explicit `outputLocation` calls):

| Format | Path (relative to root `build/`) |
|--------|-----------------------------------|
| XML | `build/reports/jacoco/overallCoverage/jacocoOverallCoverageReport.xml` |
| HTML | `build/reports/jacoco/overallCoverage/html/` |

The aggregated verification task `jacocoOverallCoverageVerification` enforces the
`overallMinimum` line-coverage floor but emits no report of its own.

### JUnit test results — two distinct directories

The `test` task the gates depend on is Gradle's standard `Test` task, which writes results
to two **separate** locations. A CI system that ingests test results usually needs the XML;
humans open the HTML. These are not the same directory:

| Format | Path (per module) | Purpose |
|--------|-------------------|---------|
| XML (JUnit) | `build/test-results/test/*.xml` | Machine-readable — feed to the CI test reporter (JUnit XML) |
| HTML | `build/reports/tests/test/index.html` | Human-readable test report |

These are Gradle `Test`-task conventions (not overridden by the plugin); `qualityCoverage`
reaches them by depending on each module's `test` task (`TaskRegistrar.registerQualityCoverage`).

### Collecting reports in non-GitHub CI

Glob patterns that capture everything above across all modules:

```
**/build/reports/**            # detekt, ktlint, checkstyle, pmd, spotbugs, codenarc, jacoco, kover HTML/XML
**/build/test-results/test/*.xml   # JUnit XML for the CI test reporter
build/reports/jacoco/overallCoverage/**   # aggregated multi-module JaCoCo (root)
```

Point your CI's JUnit reporter at `**/build/test-results/test/*.xml` (not
`build/reports/tests/**`, which is HTML), archive `**/build/reports/**` as artifacts, and
feed `build/reports/jacoco/overallCoverage/jacocoOverallCoverageReport.xml` (or per-module
`build/reports/kover/report.xml`) to a coverage dashboard.
